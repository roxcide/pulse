# PULSE — GitHub → Cloudflare Workers + D1

Приложение содержит React-интерфейс и сервер авторизации на Cloudflare Workers. Аккаунты, сессии и тренировки хранятся в D1. Supabase не используется.

**Просто загрузить папку `dist` теперь недостаточно:** для регистрации и сохранения нужен Worker из этого репозитория. Используй существующий проект Workers; статические Pages / Direct Upload не запускают этот API.

## 1. Подготовить репозиторий

Загрузи содержимое `release/pulse-admin.zip` в корень GitHub-репозитория (не сам ZIP). Сохрани скрытые файлы `.github`, `.gitignore`, `.node-version`, `.dev.vars.example`. Не загружай `node_modules`, `.wrangler`, `.dev.vars`, `dist` или `release`.

Если обновляешь старую версию, удали из репозитория прежние `.env.example` и `src/auth/config.js`: они относились к Supabase. Остальные файлы замени версиями из архива, включая `pnpm-lock.yaml`, `wrangler.jsonc`, `server`, `scripts` и `migrations`.

Локально нужны Node.js 24.19+ (24.x) и pnpm 11.25.0:

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm run deploy:check
```

`deploy:check` собирает Vite и Worker без публикации. `build.command` автоматически создаёт `dist`, поэтому прежняя ошибка `assets.directory does not exist` устранена. В `pnpm-workspace.yaml` разрешены build scripts для `esbuild` и `workerd`; запускать интерактивный `pnpm approve-builds` в Cloudflare не нужно.

## 2. Автоматическое подключение D1

В конфигурации указаны binding `DB` и имя базы `pulse-db`, без фиктивного `database_id`. При `pnpm run deploy` Wrangler подключит существующую базу с этим именем или создаст её в аккаунте Cloudflare. Затем скрипт автоматически применит миграции из `migrations/`. Повторные запуски пропускают уже применённые миграции.

Это штатный механизм [автоматического создания ресурсов Wrangler](https://developers.cloudflare.com/changelog/post/2025-10-24-automatic-resource-provisioning/). Он доступен в закреплённой версии Wrangler. Токен сборки должен иметь разрешение **Account → D1 → Edit** в том же аккаунте, где находится Worker. Если Cloudflare сообщает об отсутствии прав, обнови токен сборки в настройках проекта; ключ не нужно добавлять в GitHub или код приложения.

Первый деплой завершён только после строки `PULSE: Worker published and D1 migrations applied.`: публикация создаёт базу, следующий шаг создаёт таблицы. Если миграция завершилась ошибкой, команда вернёт ненулевой код; исправь причину и повтори деплой. Опубликованный Worker при этом уже существует, поэтому не открывай регистрацию до успешного окончания миграций.

Для локальной публикации сначала выполни `pnpm exec wrangler login`, затем `pnpm run deploy`. В Cloudflare Builds вход выполняется через токен сборки.

Если твоя действующая база называется иначе, сохрани её реальный `database_id` в `wrangler.jsonc` или укажи её имя вместо `pulse-db`; не переключай работающий проект на пустую базу. Нулевой UUID из старого архива использовать нельзя.

Ручное применение миграций при необходимости: `pnpm run db:remote`. В схеме нет демонстрационных пользователей и тренировок. Если база показывает 0 таблиц, открой D1 → pulse-db → Console и выполни содержимое `migrations/0001_auth.sql`, либо выполни `pnpm run db:remote`. Создание таблиц использует `IF NOT EXISTS`: повторное выполнение не удаляет записи. Dry-run не создаёт облачную базу и не выполняет миграции.

## 3. Настроить Worker и основной адрес

Имя `name` в `wrangler.jsonc` должно совпадать с именем твоего Worker.

В Cloudflare **Workers & Pages → Worker → Settings → Variables and Secrets** добавь runtime-переменную `APP_ORIGIN`: полный основной адрес сайта, например `https://pulse.example.com`, **без завершающего `/` и без пути**. Можно использовать основной HTTPS-адрес `workers.dev`. Это не `VITE_*` и не переменная только этапа сборки.

`keep_vars: true` в Wrangler сохраняет обычные переменные, добавленные через Dashboard, при следующем деплое. Секреты остаются в Cloudflare.

OAuth callback и проверка Origin используют именно этот адрес. Preview-домены не смогут работать с production-аккаунтами: для них нужен отдельный Worker, отдельная база и свои настройки. При смене домена обнови `APP_ORIGIN` и redirect URI у провайдеров.

Для входа по паролю планируй **Workers Paid**: scrypt намеренно требует вычислительного времени, а Workers Free ограничен 10 мс CPU на запрос. Не уменьшай стоимость хеширования ради обхода лимита. См. [лимиты Cloudflare Workers](https://developers.cloudflare.com/workers/platform/limits/).

## 4. Письма через Brevo

Добавь в Runtime variables and secrets исполняемого Worker:

- Secret **BREVO_API_KEY** — API-ключ Brevo. Не добавляй ключ в GitHub, React или VITE-переменные.
- Variable **EMAIL_FROM** — noreply@pulser.pp.ua.
- Variable **APP_ORIGIN** — https://pulser.pp.ua, без завершающего слеша.

В Brevo домен и отправитель PULSE <noreply@pulser.pp.ua> должны быть подтверждены. Письма отправляет Worker через HTTPS API Brevo, без дополнительных библиотек. Cloudflare Email Sending и binding EMAIL не используются.

После регистрации приходит письмо с шестизначным кодом на 10 минут. Введи код в том же браузере — почта подтвердится и сразу откроется аккаунт, без повторного ввода пароля. Форма восстанавливается при обновлении страницы. Новый код заменяет предыдущий; максимум 5 попыток ввода за 10 минут на аккаунт, повторная отправка не сбрасывает лимит. В другом браузере сначала введи email и пароль через «Войти», чтобы начать новое подтверждение. Пароли регистрации и сброса — от 8 до 128 символов. Новые аккаунты получают нулевую статистику. Если отправка не удалась, остаётся форма с кнопкой повторной отправки. Повторная регистрация не перезаписывает аккаунт.

Кнопка «Не помню пароль» отправляет одноразовую ссылку на 30 минут. После смены пароля все прежние сессии и ссылки отзываются, тренировки сохраняются. Ответ формы одинаков для существующего и отсутствующего адреса. Аккаунты, созданные только через Google, восстанавливаются через Google и не получают пароль этим способом.

Старые аккаунты без подтверждённой почты должны подтвердить её при следующем входе по паролю; существующие сессии действуют до истечения или сброса пароля. Если старый пароль забыт, доступен сброс. Повторная отправка ограничена одним запросом в минуту и пятью в час на адрес. В D1 хранится хеш кода, связанный с аккаунтом и защищённой HttpOnly cookie браузера. Сброс пароля по-прежнему использует ссылку с токеном во фрагменте URL; открытие ссылки само по себе её не использует. Старые ссылки подтверждения больше не принимаются: для нового кода введи email и пароль через «Войти».

При ошибках отправки смотри Worker Logs: verification_mail_failed / auth_mail_failed / auth_request_failed, без паролей, токенов и API-ключа. Статус ready в /api/auth/config означает наличие конфигурации, а не гарантию доставки. Доставку и отказы получателя проверяй в Brevo → Transactional → Logs.

Документация: [Brevo transactional API](https://developers.brevo.com/reference/send-transac-email).

## 5. Вход через Google

В Google Cloud Console настрой OAuth consent screen и создай OAuth Client типа **Web application**.

- Authorized JavaScript origin: твой `APP_ORIGIN`.
- Authorized redirect URI: `https://ТВОЙ-ДОМЕН/api/auth/callback/google`.
- Для приложения в режиме Testing добавь свои тестовые аккаунты; для публичного входа заверши публикацию/проверки, которые запросит Google.

Добавь в **Worker Secrets**:

```sh
pnpm exec wrangler secret put GOOGLE_CLIENT_ID
pnpm exec wrangler secret put GOOGLE_CLIENT_SECRET
```

Значения вводятся по запросу CLI. Не помещай их в React, GitHub, `VITE_*` или архив. После настройки кнопка Google включается автоматически.

Документация: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).

## 6. Способы входа

Доступны Google и email/пароль. Кнопка и серверные маршруты Apple удалены.

При первом входе через Google аккаунт создаётся автоматически, при следующих входах открывается тот же профиль. Аккаунты Google и email/пароль не объединяются автоматически по совпадению адреса: используй способ, которым зарегистрировался. Это защищает от захвата аккаунта через неподтверждённую регистрацию.

## 7. Подключить сборку из GitHub

В Cloudflare Workers подключи репозиторий и задай:

| Поле           | Значение                                            |
| -------------- | --------------------------------------------------- |
| Root directory | Корень с `package.json`                             |
| Build command  | Можно оставить пустым: Vite запускается из Wrangler |
| Deploy command | `pnpm run deploy`                                   |
| `NODE_VERSION` | `24.19.0`                                           |
| `PNPM_VERSION` | `11.25.0`                                           |

Миграции D1 выполняются автоматически командой `pnpm run deploy`. Не заменяй её на прямой `wrangler deploy`, иначе этот шаг будет пропущен. Секреты задаются для исполняемого Worker; наличие их только в Build variables недостаточно. GitHub Actions проверяет форматирование, тесты и dry-run, но не публикует приложение.

## 8. Проверить после публикации

1. Открой `/api/auth/config`: `checks.database: "ready"` (проверяется наличие таблиц и колонок), `configured: true`; `passwordRegistration: true`, `passwordRecovery: true`, `checks.email: "ready"`; включённые провайдеры `true`. Значения секретов endpoint не раскрывает.
2. Зарегистрируйся по email и паролю, введи код из письма и убедись, что аккаунт открывается сразу. Проверь «Не помню пароль», установи новый пароль и убедись, что старый больше не подходит.
3. Убедись: история и планы пустые, тренировок/часов/поднятого веса — 0, недельная цель не задана. Каталог упражнений и программы являются шаблонами, а не личной историей; стартовые рабочие веса — 0.
4. Выбери программу, выполни подход, заверши тренировку и дождись «Сохранено в облаке». Обнови страницу — запись должна сохраниться.
5. Выйди, войди в другой новый аккаунт и проверь пустую историю.
6. Проверь повторный вход с паролем и Google на основном домене.

## Локальная разработка

```sh
pnpm run db:local
```

Скопируй `.dev.vars.example` в `.dev.vars` и запусти `pnpm run dev:worker`. Открывай **http://localhost:8787**: это значение `APP_ORIGIN` в примере. `.dev.vars` игнорируется Git. Локальная D1 находится в `.wrangler` и никогда не публикуется.

Для HMR запусти Worker с `APP_ORIGIN=http://localhost:5173` в `.dev.vars`, затем во втором терминале `pnpm dev` и открывай localhost:5173. Vite проксирует `/api` к Worker. `pnpm preview` показывает только статическую сборку и не запускает API.

Для локальной отправки задай BREVO_API_KEY и EMAIL_FROM в игнорируемом .dev.vars. Автотесты используют подменённый транспорт и не рассылают настоящие письма. При ручной регистрации локальный Worker использует настоящий Brevo, если в .dev.vars указан рабочий ключ.

## Данные и ограничения версии

- Пользователь определяется только серверной сессией; запрос не может выбрать чужой `user_id`. Каждый аккаунт получает отдельное состояние D1. Старые общие `pulse-*` записи localStorage не импортируются.
- Пароли: scrypt с индивидуальной солью. В D1 лежат хеши паролей и токенов; браузер хранит только HttpOnly session-cookie, срок — 7 дней.
- Изменения отправляются автоматически. При ошибке они остаются в памяти открытой вкладки, появляется кнопка повтора, выход блокируется до сохранения. Полноценного офлайн-режима нет; не закрывай страницу с несохранёнными изменениями.
- При одновременном редактировании на разных устройствах последнее сохранение каждого раздела побеждает; совместное редактирование и автоматическое слияние не реализованы.
- Валидация ограничивает размер запроса 2 МиБ и число элементов. Хранение истории — до 10 000 тренировок, в зависимости от размера записей; для больших объёмов потребуется разнести записи по отдельным таблицам.
- Ограничение частоты работает через D1. Ежедневный Cron удаляет истёкшие сессии, токены и счётчики. История тренировок этим заданием не удаляется.
- Тесты проверяют регистрацию с подтверждением почты, CSRF, истечение сессий, выход, разделение аккаунтов, OAuth state и ошибки сохранения. Реальный Google-вход проверяется с настройками владельца.

## Темы и гостевой режим

В настройках и на экране входа доступны PULSE, Mocha (мягкая тёмно-коричневая), Alduin, 80s After Dark и 8008. Dualshot удалена. Тема применяется сразу, включая кнопки, формы, карточки и мобильную навигацию; выбор хранится в этом браузере.

Кнопка «Войти как гость» находится под регистрацией и доступна также во время ожидания сервиса входа. Аккаунт для неё не требуется. Гость получает пустую историю, нулевые показатели и весь интерфейс тренировок. Гостевой прогресс хранится в localStorage, отдельно от данных аккаунтов, и сохраняется после обновления страницы. Очистка данных сайта удаляет гостевой прогресс. При недоступном хранилище приложение предупреждает, что изменения не сохранены.

В окне аккаунта гостя кнопка «Войти или зарегистрироваться» возвращает на экран входа. Гостевые данные не отправляются в D1 и не копируются в аккаунт автоматически; возвращение в гостевой режим открывает прежний локальный прогресс. Зарегистрированные пользователи продолжают работать с отдельными облачными данными.

Гостевой режим не требует почтового сервиса или серверного хеширования пароля. Офлайн-кэш загрузки самого сайта не добавлен; для первого открытия страницы нужен доступ к сайту. Одновременное редактирование гостевых данных в нескольких вкладках не объединяется — последнее сохранение заменяет предыдущую версию.

## Настройки, цель и удаление аккаунта

Настройки (шестерёнка) содержат тему оформления, имя и отдых между подходами. «Изменить цель» на главной открывает отдельную форму только с количеством тренировочных дней в неделю (1–7 или «Не задана»). Изменение одной формы сохраняет значения другой.

Аватар открывает окно аккаунта с выходом и удалением. Удаление доступно зарегистрированным пользователям, в том числе Google. После предупреждения нужно ввести email аккаунта и нажать «Удалить навсегда». Удаляются запись пользователя, привязки Google, все сессии, коды/ссылки подтверждения и восстановления, а также всё состояние тренировок в D1. Сервер использует текущую сессию и X-Pulse-Account, проверяет Origin и подтверждение. Новая регистрация создаёт отдельный пустой аккаунт; функции восстановления удалённого аккаунта нет. Настройка темы браузера и отдельные данные гостя сохраняются.

Перед удалением приложение останавливает отложенное автосохранение и ожидает уже выполняющийся запрос. Ошибка сохранения не блокирует намеренное удаление. Если само удаление не удалось, окно остаётся открытым с ошибкой и возможностью повтора. Гостям удаление аккаунта не предлагается. Для обновления не нужны новые секреты или миграции базы.

## Оформление кода подтверждения

Код отображается в шести отдельных ячейках. Поддерживаются ввод и исправление с клавиатуры, вставка полного кода и автозаполнение one-time-code. При неверном или истёкшем коде ячейки подсвечиваются красным и коротко встряхиваются; при редактировании ошибка сбрасывается. После успешного ответа сервера ячейки последовательно загораются зелёным, а через 0,8 секунды открывается аккаунт. Сетевые ошибки не помечают код неверным. При prefers-reduced-motion анимации отключены, цвета и текстовые подсказки сохраняются.

## Каталог и подходы

В библиотеке 35 упражнений. Нажатие на название открывает технику, частые ошибки и подсказку; описание доступно также в текущей тренировке. У своих упражнений можно сохранить и изменить заметки о технике. Новые упражнения добавляются к старому каталогу при загрузке, без изменения рабочих весов, пользовательских упражнений и истории.

Кнопка корзины справа от подхода удаляет только этот подход из текущей тренировки, включая отмеченный выполненным. Прогресс и итоговый объём пересчитываются. После удаления последнего подхода остаётся кнопка добавления. Изменения сохраняются в D1 или в хранилище гостя, как и остальные данные тренировки. Новые SQL-миграции для этого обновления не нужны.

Материалы для сверки базовой техники: [жим лёжа — NASM](https://www.nasm.org/resource-center/exercise-library/barbell-bench-press), [отжимания — NASM](https://www.nasm.org/resource-center/exercise-library/push-up), [подтягивания обратным хватом — ACE](https://www.acefitness.org/resources/everyone/exercise-library/190/chin-ups/).

## Админ-панель

После публикации войди в подтверждённый аккаунт `uvukostya@gmail.com` и нажми значок щита в верхней панели либо открой `/#admin`. Сервер назначает права только этому подтверждённому адресу; гостевой режим, имя в профиле и данные браузера прав не дают. Дополнительные runtime-переменные не нужны. После обновления перезагрузи сайт, чтобы получить актуальные права из сессии.

В панели доступны поиск и постраничный список пользователей, имя, email, статус подтверждения, блокировка входа, установка нового пароля, недельная цель, время отдыха и JSON-редактор истории, упражнений, расписания, планов и активной тренировки. Текущие пароли и хеши не выдаются. Изменения и удаления записываются в журнал без паролей и токенов. Аккаунт владельца защищён от изменения и удаления через эту панель.

Сохранение завершает предыдущие сессии выбранного пользователя. Смена email снимает подтверждение и отключает прежнюю Google-привязку; для аккаунта, входившего только через Google, потребуется задать пароль. Новый email подтверждается штатным кодом при входе. Блокировка прекращает вход как по паролю, так и через Google. Удаление требует ввода email выбранного аккаунта и удаляет его личные данные каскадно. Журнал админ-действий остаётся.

Для панели обязательна миграция `migrations/0002_admin.sql`: новые поля пользователей, журнал и счётчик версий. `pnpm run deploy` применяет её автоматически после публикации Worker. Дождись `PULSE: Worker published and D1 migrations applied.` При ошибке выполни `pnpm run db:remote` и проверь успешное применение обеих миграций. Не выполняй ALTER TABLE вручную повторно: Wrangler отмечает выполненные миграции. Действующую D1 не удаляй. При ручном обновлении существующего Worker можно сначала применить миграцию, а затем опубликовать код, чтобы избежать краткого периода несовпадения схемы.

Открытая карточка содержит версию данных. Если пользователь или другая вкладка изменили их, сервер отклоняет устаревшее сохранение целиком. Нужно загрузить свежую карточку и повторить правки. Сохранение аккаунта, отзыв сессий и запись журнала выполняются одной [транзакцией D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).
